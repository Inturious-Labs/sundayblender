# fetch_image.sh — Known Issues (fix before committing)

## BUG: URLs containing literal `$` get mangled → confusing 404

**Status:** OPEN — must fix before committing the script.

**Symptom:** A correctly-quoted image URL with `$word` segments in the path
(common in Cloudinary / ffx.io transformation URLs, e.g.
`.../images/$zoom_1%2C$width_3000%2C.../...`) is silently corrupted. Example:

- Passed:   `.../images/$zoom_1%2C$multiply_1%2C$width_3000%2C.../...`
- Resolved: `.../images/%2C%2C.777778%2C%2C%2C/...`  ← every `$word` deleted
- Result:   `Download failed (HTTP 404)`

**Root cause:** The `$word` segments are treated as shell variable
references and expand to empty. NOT a user quoting error — `"$URL"` in
double quotes still undergoes `$` expansion. The mishandling is inside the
script's string processing.

**Prime suspect:** `urldecode()` uses `printf '%b' "${data//%/\\x}"`.
`%b` interprets backslash/escape sequences — wrong for arbitrary URL bytes.
Also audit every place the URL is re-emitted (`printf '%s' "$url"`
passthrough, command-substitution boundaries) to ensure no expansion context
re-evaluates it.

**Fix direction:**
- Replace `urldecode` with a `%XX`-only decoder that does not interpret
  backslash escapes and never re-expands `$`.
- Verify a URL with `$`, `\`, backticks, and `%XX` round-trips byte-identical
  through `resolve_source_url` for BOTH the Google-redirect branch and the
  direct passthrough branch.

**Note:** Latent — only triggers on URLs with literal `$`. A different link
working does NOT mean this is resolved.
